# Processor runs as a Flink job

The processor — decode `events.raw`, fold it into per-aircraft snapshots on `aircraft.state` — is an Apache Flink job (`flink/`), the only JVM component in an otherwise Go and Python system. It replaced an in-process Go loop that kept aircraft state in memory and rebuilt it on every start or rebalance by reading the compacted `aircraft.state` topic back to its end (last present at commit `913e240`). That design made the output topic double as the state store, which forced its shape onto the fold: snapshots had to go to the same partition number their input came from, the topic had to be compacted, per-field timestamps couldn't survive a restart because they weren't on the wire, and a crash replayed the uncommitted batch on top of state that already included it, so `messages` over-counted. Flink's checkpointed keyed state removes all of that, and its transactional Kafka sink commits state and output together, so a crash produces neither duplicate snapshots nor drift in counts. The price is a Maven build stage, two containers with ~1 GB heap each, a checkpoint volume that must be as durable as Kafka, and output that lags by the checkpoint interval for `read_committed` consumers.

## Considered options

- **In-process Go loop, state rebuilt from the compacted topic.** Zero extra infrastructure and Kafka is the only durable store, but the output format becomes the persistence format and replay isn't idempotent. Correct enough for a live map; not for exact counts or private state.
- **Go loop with its own state store** (e.g. an embedded KV or Postgres) for exact recovery. Reimplements checkpointing, transactional output and rebalance-aware state migration by hand — the parts Flink already has.
- **Flink** — chosen. The processor is the one stateful stream computation in the system; the framework's cost is paid once, and any future stateful derivation (per-station stats, flight segments) lands in the same job rather than growing another hand-rolled state loop.
